### 1. The Tecno LH7n vs MT6833 Kernel Difference

- **What MillenniumOSS did:**
  They pulled Mali blobs (`libGLES_mali.so`, `vulkan.mali.so`) from the Motorola Moto G35 (`XT2513-1`, `kansas`, MT6835 / Dimensity 6300, Android 15), dropped in `mali_platform.config`, the Gralloc AFBC XMLs, and added the `ro.vendor.arm.egl.configs.*` HAL format mappings in `vendor.prop`.
- **Why it worked out-of-the-box for them:**
  Tecno LH7n runs on **Linux 5.10 GKI** (`android_kernel_common_android12-5.10`). Its kernel `mali_kbase` is already updated and natively understands the newer IOCTL ABIs that newer unified `libGLES_mali.so` binaries use.
- **Why doing the same crashes on our everpal:**
  Our device is on **Linux 4.14.357-Aqua**. The 4.14 stock kernel driver is `mali-r32p1`. When a newer monolithic `libGLES_mali.so` is loaded by SurfaceFlinger, IOCTL command mismatches cause SurfaceFlinger to immediately SIGSEGV / crash.

---

### 2. How We Solved It: Hybrid Decoupled Architecture

Instead of fighting SurfaceFlinger on 4.14, we decoupled the graphics stack:
1. **Rock-Solid System GLES:**
   We keep stock `libGLES_mali.so` (r32p1) exclusively for SurfaceFlinger and HWUI system rendering. Zero crashes, zero display regressions.
2. **Dedicated Valhall Vulkan 1.3 ICD:**
   We deployed a standalone **Valhall r49p1 Vulkan 1.3 ICD** (`libVK13_mali.so`) extracted directly from **Redmi Note 13 5G / 13R Pro (`gold`, Dimensity 6080 / MT6833)** on **HyperOS 3.0 Android 15** (`OS3.0.10.0.VNQCNXM`).
3. **Mali-G57 Hardware Architecture Fact:**
   Mali-G57 (Valhall v1) uses the **Job Manager (JM)** interface (`BASE_UK_VERSION_MAJOR 11`), **NOT** CSF (Command Stream Frontend). Because shader and pipeline compilation runs 100% in user-space in the ICD driver, it runs natively on Linux 4.14 without hitting kernel bottlenecks!
4. **Linker Hooks & AFBC:**
   - Patched companion `libgpd1.so` to export the missing `GpuAuxBlitAHardwareBuffer` symbol via bit-exact Bionic GnuHash.
   - Calibrated Arm Generic Timer frequency to 13 MHz (`PLATFORM_AGT_FREQUENCY_KHZ=13000`).
   - Integrated full Gralloc AFBC manifests (`cam.xml`, `dpu.xml`, `dpu_aeu.xml`, `gpu.xml`, `vpu.xml`) and `mali_platform.config`.
   - Injected the EGL pixel format mappings from the Motorola reference into `vendor.prop`.

### 3. About the "Capped" 3DMark Benchmark Question

If you noticed 3DMark Sling Shot Extreme reporting "30.30 FPS (Capped)":
- The 3DMark physics simulation engine caps physics step ticks at 33.0 ms ($1000 / 33 = 30.30$ FPS max engine rate).
- Because our Cortex-A76 Big cores were pinned at sustained 2.40 GHz with sconfig 10, all 3 physics sections completed calculations way faster than 33 ms and hit the maximum frame rate ceiling on all 3 sections ($30.30$ FPS), giving us the **`4,053` World Record Physics score**!
- The overall benchmark is NOT capped (`capped: false` in database), achieving **2,736 pts** in GLES 3.1 and **2,734 pts** in Vulkan.

### 5. Kernel Backport Notes (For 4.14 if backporting 5.10 mali_kbase)

If you still want to port the full 5.10 `mali_kbase` into 4.14 so that a single unified `libGLES_mali.so` can be used:
1. **`access_ok()` API shim:** 4.14 takes 3 arguments: `access_ok(VERIFY_READ, addr, size)` whereas 5.0+ takes 2 arguments: `access_ok(addr, size)`. Wrap this with a compat macro.
2. **ION Buffer Allocator:** 4.14 uses ION for graphic buffers. In `mali_kbase_mem_linux.c`, retain the `#ifdef CONFIG_ION` allocator paths from `mali-r32p1` instead of relying solely on modern `dma_buf_map_attachment`.
3. **Fence Deadlines:** Modern DDKs call `dma_fence_set_deadline()`. Guard or stub this since 4.14 sync fences lack deadline hints.
4. **MediaTek Glue:** Retain `platform/mt6833/` and `platform/mtk_platform_common/` from `mali-r32p1` to maintain GED and DVFS integration.

Feel free to inspect the commits, cherry-pick what you need, and test! Let me know if you run into any hurdles. 🚀
